## 2. scene42 동결과 카운터 정정

조회 경로: `/app/data/pilots/usage_metering_20260827_scene42/request_ledger.json`.
원장 SHA-256은 직전 보고서와 동일한
`f9f016644e9f4288bd3f754d2d9caeea3a5a6e00c26f1cec6b5f6af9aea9daa3`이다.
SQLite를 `mode=ro`로 조회한 결과:

```json
{
  "count": 2,
  "failure_n": 2,
  "next_allowed_at": 1787762034.2775416,
  "active": null,
  "status": "needs_review"
}
```

잠금 해제·카운터 초기화·장면 재명명·다른 원장으로 복제하지 않았다.
이는 이 턴에서 해당 파일럿을 호출하지 않았다는 뜻이지, 별도 전역 scene42 차단 장치를 추가했다는 뜻은 아니다.

백오프의 `n`은 **계산 전 실패 수**다. 두 번째 실패 처리에서
`B=min(300, 20×2^1)=40`, `delay=U(20,40)`을 계산한 뒤 `failure_n=2`를 저장했다.
따라서 `20×2^2`의 절반~전체가 20~40초라는 설명은 산술적으로 틀리다. 그것은 40~80초다.
실제 구현은 장면/프로젝트의 이전 실패 번호 중 큰 값을 쓰므로 두 상태를 함께 보존해야 한다.

## 4. 텍스트 계약의 실제 미완료 지점

### A. 정보성/장식성이 아닌 수치/비수치 분기

`app/utils/image_text_contract.py::build_scene_text_contract`는
`contains_financial_number`만으로 `generated_texts`와 `deterministic_texts`를 나눈다.
같은 분기가 `app/v5/scene/runtime_contract.py::plan_v5_scene_contract`와
`app/workers/images_worker.py`의 프롬프트 구성에도 각각 존재한다.
**한 함수만 바꾸면 생성 프롬프트와 후처리 계약이 서로 달라질 수 있다.**

현재 함수를 직접 호출한 진단 결과:

| 승인 문자열 | 현재 경로 | 승인된 WO-IMG-01 요구 |
|---|---|---|
| 삼성전자 | 모델 생성 | 정보성 → 결정론 |
| KOSPI | 모델 생성 | 정보성 → 결정론 |
| 현재 전망 | 모델 생성 | 정보성 → 결정론 |
| 143조 원 | 결정론 | 결정론 |
| 와! | 모델 생성 | 실측 전 장식성 → 결정론 기본값 |

이는 “한국어를 금지”하거나 “모델이 문자를 쓰면 무조건 실패”라는 정책이 아니다.
정보성 원문은 검증된 내용 그대로 보존하고, 그림 속 실제 소품 표면에 적절한 크기/원근으로 합성한다.
장식성 생성은 승인 문자열+언어/길이/크기별 실측 근거가 있을 때만 별도 선택 경로로 열어야 한다.
현재 visual QA 지시에도 비수치 내레이션 문자열과 PRESS/MARKET/OUTLOOK 같은 문구를 넓게 허용하는 규칙이 남아 있어,
분류/생성/렌더/QA가 하나의 정책 버전을 참조하도록 연결해야 한다.

### B. 정확 일치로 볼 수 없는 OCR 통과

`visible_text_contract_result`의 중간 OCR 검사는 승인 문자열과 **양방향 부분 문자열** 비교를 한다.
`삼성전자오탈`은 승인 `삼성전자`를 포함하므로 이 함수에서 `passed=true`, 추가 검수 목록도 빈 값이다.
다른 오탈자 `SK 하이느`는 검수 목록에 들어가지만 `passed=true`다. OCR이 아무것도 못 읽어도 이 중간 함수는 통과한다.
중간 통과가 후속 멀티모달 QA의 최종 승인을 증명하지 않는다는 구분이 필요하다.

더 중요한 것은 `app/services/final_frame_text_integrity.py::inspect_final_frame_text_integrity`다.
공백을 제거한 OCR 문자열에서 예정 문자열이 **포함돼 있는지** 검사하므로 다음 두 사례가 최종 대조 함수에서도 통과했다.

| 예정 문구 | 가짜 OCR 결과 | 기대 | 실제 함수 결과 |
|---|---|---|---|
| 4배 | 14배 | 거절 | 통과 |
| 영업이익 | 비영업이익 | 거절 | 통과 |
| PER | per | 거절 | 거절 |
| 현재 전망 | 현력 토공 | 거절 | 거절 |
| 143조 원 | 143조 + 줄바꿈 + 원 | 허용 | 허용 |

진단은 **가짜 OCR 행을 실제 함수에 주입**한 것이며 새 이미지/실제 OCR/모델 출력은 아니다.
픽셀 계보 예외를 사용하지 않았는데도 앞의 두 오류가 통과했다. 전체 영상이 반드시 잘못 승인됐다고 확대 해석하지 않는다.

후속 수정은 표면별 예정 문자열과 관측 문자열의 정확한 대응을 만들고, 허용된 줄바꿈/공백 외 글자·숫자·단위를 보존해야 한다.
PSM 6/11/13 결과가 현재 합쳐지는 점도 고려해 **판독 시도별 결과를 따로 대조**해야 한다.
단순히 전체 OCR 문자열을 하나로 이어서 `==`로 바꾸면 정상적인 여러 표면/여러 OCR 시도까지 깨질 수 있다.

### C. 표면·가독성 검증 부품과 남은 연결

좋은 기존 구현은 유지한다:

- 승인 문자열의 text hash와 합성 영역 pixel hash 기록.
- 안전한 물리 표면을 못 찾으면 임의 고정 좌표로 덮지 않고 실패 처리.
- 렌더 후 crop이 변조되면 픽셀 계보 예외로 통과시키지 않음.
- 별도의 warp compositor에 quad/가림 보존 테스트가 있음.

다만 일반 캡션 경로 `_apply_deterministic_surface_caption`는 검출 quad를 min/max 사각형으로 축약하고
`add_surface_caption`을 호출한다. 이 함수는 축 정렬된 영역 중앙에 글자를 그리며 원래 quad로 투시 변환하지 않는다.
별도 warp 구현이 있다는 이유로 **모든 정보성 캡션의 원근이 이미 해결됐다**고 볼 수 없다.
현재 캡션 메타데이터도 단일 `deterministic_text_regions`로 저장하므로, 다중 표면별 책임을 연결해야 한다.

`font_size>=24`는 픽셀 계보 보완의 조건일 뿐 프레임 대비 실제 glyph 높이 조건이 아니다.
WO의 2.5%/4%/6%는 실험 버킷이며 검증된 허용 임계값 X가 아니다.
검토한 캡션/타이포그래피/최종 검사 경로에서 글자별 폰트 cmap 커버리지와 변환 후 실제 glyph 높이 판정을 확인하지 못했다.
원문/hash 일치만으로 폰트 누락·잘림·작은 글자 가독성까지 보증하지 않는다.

## 5. 48장 승인 내레이션의 오프라인 추출 재현

입력은 과거 `scene_generation_contracts.json` 48행이며 SHA-256은
`72dd95c1f577acca6793d850567d045c28c7a0e5cd05f3229d9d105c8dc8cdf6`이다.
기존 `attach_scene_screen_texts`와 텍스트 계약 함수만 메모리에서 호출했다.

- 48/48 내레이션 해시 불변, 입력 파일 및 입력 객체 불변.
- 현 계약상 생성 문구가 있는 장면 19개, 결정론 문구가 있는 장면 14개. 두 집합은 겹친다.
- 자동 추출 결과가 빈 장면 21개.
- 이 입력에서 명시 `screen_text_plan`이 있는 장면 0개.

빈 추출은 “그 장면에는 텍스트가 필요 없다”거나 “영어가 금지”라는 판정이 아니다.
예를 들어 scene26의 `주성엔지니어링`, scene35의 `전망치`는 내레이션에 있지만 현재 짧은 용어 목록으로 추출되지 않는다.
누락을 발견했다고 모든 단어를 화면에 올릴 것이 아니라, 필요한 정보성 문구와 소품 표면을 장면 단위로 명시해야 한다.
통합 메타데이터의 다른 버전 또는 과거 전체 실행에서 표면 계획이 없었다고 일반화하지 않는다.

진단 스크립트: `backend/fastapi-workers/scripts/audit_image_text_readiness.py`.
현재 코드 7개 파일 hash, 48장 원문 hash, 라우팅/가짜 OCR 반환 객체는
[재현 JSON](evidence/wo_img01_readiness_20260827/text-readiness.json)에 보존했다.
네트워크 connect를 차단한 별도 프로세스에서 실행했다.

## 6. 8장 파일럿으로 계측을 옮기는 실행 조건

계측을 별도 scene42 반복 작업으로 밀어붙이지 않고 공통 호출 경로에서 수집하는 방향에 동의한다.
단, 8개 요청은 공급자 상태를 공유하므로 독립 시행이라고 가정하거나 “몇 장은 반드시 성공”한다고 보장하지 않는다.

### 대상 후보 — 아직 유료 실행 승인 명세 아님

| 원본 장면 | 파일럿 검증 목적 | 현재 자동 추출에서 확인한 준비 과제 |
|---|---|---|
| 00 | 숫자/기업명 도입, 저울·대상 소품 관계 | PER 및 기업·배수의 표면 계획 |
| 01 | 숫자만 강조한 구성 방지 | 4배가 무엇의 배수인지 맥락 보존 |
| 05 | 생산/반도체 내용과 비교 | 소품·행동을 중심으로 문구를 보조 배치 |
| 07 | 회사명/지수명/한글/복합 수치 | 영업이익·제외 조건 포함 의미 관계 보존 |

| 26 | 기업명/순위·다중 표면 | 현재 빈 추출, 필요한 이름의 명시 계약 |
| 35 | 전망 하향/한국어 오탈자 | 현재 빈 추출, 필요한 전망 문구 명시 |
| 47 | 결론/불필요한 말풍선 방지 | 현재 빈 추출, 필요 문구만 근거 연결 |

이 후보는 서로 다른 8개 원본 장면이고 scene42를 포함하지 않는다. 번호를 0~7로 다시 붙이지 않고 원본 번호와 내레이션 hash를 유지한다.
Job52의 기존 이미지를 덮지 않으며, 옛 오염 `prompt_en`을 무조건 재사용하지 않는다. 새 텍스트/엔티티 계약에서 프롬프트를 구성하고
기존 양호한 화풍/장면 역할은 보존한다. Claude 기획이 필요하면 그 호출/비용도 승인 범위에 넣어야 한다.

실행 전에 필요한 것:

1. 단일 파일럿 원장/고정 scene 키 + 원본 index/내레이션 hash/계약 hash/참조 hash가 있는 명세.
   같은 scene42의 이름만 바꾸거나 원장 경로를 바꾸어 `needs_review`를 우회하지 않도록 원본 대응을 검사한다.

8. 원본 8장·접촉시트·문자/의미/스타일 검수 후 사용자 승인. 그 전 Fal 실행 없음.
