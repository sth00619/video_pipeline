### 4.1 후속 재검증 — 지연 시간과 재시도 대기는 구분한다

근거는 위 JSON의 `ledger_excerpt`와 `worker_retry_log_lines`다. 번호는 시간순 요청 번호이며 scene 번호가 아니다.
`시작 간격 = 다음 reserved_at - 이전 reserved_at`, `응답 후 대기 = 다음 reserved_at - 이전 completed_at`으로 계산한다.

| 요청 구간 | HTTP 결과 | 요청 소요 시간 | 해석 가능한 관측 |
|---|---|---|---|
| 1~2 | 200 2회 | 37.325~63.720초 | 두 시작 시각은 12,856.778초(약 3시간 34분) 차이. 연속 공급자 재시도로 집계하지 않음 |
| 3~14 | 504 9회, 503 3회 | 138.983~285.300초 | 응답을 오래 기다린 순차 재시도. 대부분 시작 간격이 앞 요청 소요 시간 + 대기 시간과 일치 |
| 15 | reserved 1회 | 미상 | 완료 시각이 없어 다음 요청까지의 응답 후 대기를 계산하지 않음 |
| 16~47 | 503 32회 | 3.100~18.929초 | 빠른 UNAVAILABLE 응답이 반복됨. 서버 내부 circuit 상태를 조회한 것은 아님 |

요청 16~47 내부의 31개 인접 쌍을 전수 계산하면:

- 시작 간격이 정확히 25~30초 범위인 것은 **15/31쌍**이다. 전부 또는 거의 전부 고정 25~30초였다고 쓰지 않는다.
- 응답 후 대기: **20~21.1초 20쌍, 40~42초 4쌍, 60~61초 4쌍, 120초 초과 3쌍**.
- 워커 로그에는 `20.4s → 40.7s → 60.0s`가 명시돼 있어 지수 백오프가 전혀 없었다는 결론은 틀리다.
- 공급자 호출은 `attempt=1/2` 뒤 약 20초만 기다리고 종료됐다. 다음 공급자 호출/상위 재실행에서 내부 카운터가
  다시 1로 시작해 지수식의 증가 효과가 전체 실패 연쇄에 이어지지 않았다.
- 분석 기준 커밋 `75ac1f5`에는 공급자 `min(120, base * 2**(attempt-1))`와 워커 `min(60, base * 2**attempt + U(0,1))`가 있다.
  이는 분석 기준 코드의 공식이며 과거 모든 실행의 환경변수·Retry-After 응답 헤더를 재구성했다는 뜻은 아니다.
- 따라서 정확한 결함은 **짧은 초기 대기가 반복되도록 재시도 계층과 카운터가 초기화되는 구조**다.
  이를 해결하지 않고 동시성만 낮춰도 반복 호출은 재발할 수 있다. 다중 작업의 동기화 폭주 위험은 있지만,
  이 한 장면의 순차 원장만으로 실제 thundering herd나 서버 내부 circuit 개방을 확정하지 않는다.

추가 독립 검증에서도 32개 요청이 8개씩 네 묶음으로 나뉘며, 묶음 내부 7개 대기의 근삿값은
`20,20,20,40,20,60,20`으로 반복됐다. 네 묶음의 내부 28쌍과 긴 중간 공백 3쌍을 합하면 위 31쌍과 같다.
이는 이중 계층 카운터 초기화 설명을 지지한다. `20→40→60`은 상한이 적용된 대기이므로 매 단계 정확히 두 배라는 뜻은 아니다.

후속 구현 DoD:

1. 각 POST 전에 job/scene/contract fingerprint/run ID/attempt ID/endpoint/model/tier/payload hash/참조 hash와 byte 수 기록.
2. API 키, base64 본문은 로그 금지. 응답 상태·오류 코드·요청 ID·실행 시간과 결과 이미지 hash 기록.
3. QA event가 해당 attempt ID와 이미지 hash를 참조. HTTP 실패·QA 실패·표면 합성 실패 카운터 분리.
4. 재시도는 한 계층이 소유. 영속적인 장면별 총 요청 상한 3회(최초 포함)로 재개/워커/공급자 중첩 모두 차단.
   파일럿 총예산 상한이 먼저 걸리면 3회보다 일찍 중단한다. 계약 hash만 바꿔 동일 job 누적 한도를 우회하지 않는다.
5. 초과 장면은 `needs_review`로 격리. 다른 장면 작업은 가능하되 이미지 승인/조립에는 미완료 장면이 남아 있음을 차단 조건으로 전달.
6. Redis 또는 프로세스 간 원자적 예약으로 동시 워커의 초과 호출을 방지. 프로세스 재시작 후에도 한도 유지.
7. **적응형 동시성보다 먼저 누적 지수 백오프 + jitter를 구현한다.** 위 4.1에서 확인된 짧은 초기 대기의 반복을
   단일 재시도 소유자로 모으고, 실패 번호 `n`과 `next_allowed_at`을 영속화해 재개/프로세스 재시작 때 초기화하지 않는다.
   로컬 backoff 상한은 5분이다. 예시 정책은 `B_n=min(300, base*2**n)`, `delay=U(B_n/2, B_n)`으로,
   상한 도달 후에도 jitter가 사라져 모든 요청이 동일 시각에 몰리지 않게 한다.
   구현·시험과 미배포 범위는 [WO-REQUEST-01 체크포인트](WO_REQUEST_01_IMPLEMENTATION_CHECKPOINT_2026-08-26.md)를 참조한다.
   - 유효한 Retry-After는 최소 대기 시간으로 준수한다. 5분보다 길면 5분으로 잘라 조기 재요청하지 않고 예약/보류한다.
   - 실제 수면 5분으로 워커를 점유하지 않고 예약 재개 방식으로 구현하며, 중지 플래그는 대기 중에도 반영한다.
   - 공급자/프로젝트 수준 503 냉각을 작업들이 공유하고, 장면별 총 요청 3회 상한·예산 상한을 별도로 유지한다.
   - 가짜 시계와 주입 RNG 테스트로 지수 대기 범위, jitter 분산, cap, Retry-After, 재개 후 `n`/예약 유지,
     이중 계층 재시도 부재, 다중 워커의 조기 POST 차단을 검증한다. 무작위 대기값이 매번 엄격히 증가한다고 주장하지 않는다.
   - 이 DoD 통과 후 적응형 동시성 2~3을 통제 파일럿에서 측정한다. 원인 검증 없이 전역 동시성 변경 금지.
