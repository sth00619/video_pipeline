# WO-PROVIDER-02 — Pro 대 Flash 운영 정책 심층 조사 결정

작성일: 2026-08-30
범위: 웹 조사와 기존 로컬 실측을 이용한 모델 정책 결정. 이 문서는 코드·환경·원장·유료 API를 변경하지 않는다.

## 1. 결론

**지금 영상 생성 버튼의 전역 기본 모델을 Flash로 바꾸지 않는다. 현재 Pro 기본 정책을 유지한다.**

다만 이것은 영구적인 Pro-only 결론이 아니다. 비용을 우선 제약으로 두지 않는다면 가장 빠르고 정보 가치가 높은 경로는 다음 세 단계다.

1. **현재 운영 기본값:** `gemini-3-pro-image` 유지.
2. **가용성 개선 우선 실험:** 동일 Pro에 `serviceTier=priority`를 적용한 소규모 운영 canary. 모델 분포를 바꾸지 않고 503 위험을 줄일 수 있는지 확인한다.
3. **Flash 승격 실험:** `gemini-3.1-flash-image`를 기본 minimal이 아니라 `thinkingLevel=high`로 명시하고, 정화된 참조·운영 버튼과 동일한 최종 payload로 Pro Priority와 쌍대 비교한다.

최종 구조는 전역 단일 모델 교체보다 **장면 계약에 따른 명시적 모델 라우팅**이 유력하다.

- Pro Priority 후보: 승인 문구, 사실 기반 정보 표면, 다중 참조, 캐릭터 일관성, 복잡한 구도.
- Flash High 후보: 모델이 문자를 그릴 필요가 없는 물리 비유, 움직임·배경 밀도가 중요한 장면, 빠른 탐색용 이미지.

HTTP 503을 만나면 몰래 Pro에서 Flash로 바꾸는 폴백은 허용하지 않는다. 모델·thinking·service tier는 장면 계획과 fingerprint·원장에 명시되어야 하며, 모델 변경 결과는 동일한 품질 게이트를 새로 통과해야 한다.

## 2. 왜 즉시 Flash 전환이 아닌가

### 2.1 공식 목적은 Flash의 전면 우위를 뜻하지 않는다

Google은 [이미지 생성 가이드](https://ai.google.dev/gemini-api/docs/image-generation)에서 Flash를 속도·대량 처리에, Pro를 전문 자산·복잡한 지시에 배치한다. [Pro 모델 페이지](https://ai.google.dev/gemini-api/docs/models/gemini-3-pro-image)는 특히 복잡한 그래픽 디자인, 정확한 텍스트가 필요한 사실 기반 데이터 시각화를 사용처로 든다. 이 파이프라인은 단순 이미지 생성이 아니라 승인 문자열, 금융 사실, 물리 표면, 캐릭터 정체성, 화풍, 후속 Fal 안전성까지 동시에 요구하므로 Pro의 공식 목표와 겹치는 부분이 크다.

[Flash 공식 모델 카드](https://deepmind.google/models/model-cards/gemini-3-1-flash-image/)에서는 전체 선호와 일반 시각 품질이 높지만, 객체·환경 편집, 다중입력 편집, 스타일화 같은 참조 민감 축에서는 Pro가 여전히 강한 결과가 있다. 또한 작은 글자·긴 문단, 캐릭터 일관성, 공간 관계, 환각, 간헐적 지연·타임아웃이 알려진 한계로 적혀 있다.

### 2.2 로컬 47장 비교는 Flash의 속도·가용성 이점과 품질 위험을 동시에 보였다

scene42를 동결한 47장 쌍대 비교에서:

| 항목 | Pro | Flash | 해석 |
|---|---:|---:|---|
| HTTP 200 | 44/47 (93.62%) | 46/47 (97.87%) | 이 표본에서는 Flash 우세지만 47장으로 공급자 일반 우위를 확정할 수 없다. |
| 평균 지연 | 46.46초 | 31.47초 | Flash가 약 32% 빠르다. |
| 승인 생성문자 정확 | 36/36 | 33/35 | Pro가 더 안정적이었다. Flash는 회사명 대신 로고를 쓰는 사례도 있었다. |
| thinking 토큰 | 성공 요청 합계 9,426 | 0 | Flash 요청은 `thinkingConfig`를 생략한 기본 minimal 조건이었다. |

Wilson 95% 구간은 HTTP 200 기준 Pro 약 82.84~97.81%, Flash 약 88.89~99.62%로 겹친다. 승인문자 정확성도 Pro 약 90.36~100%, Flash 약 81.39~98.42%로 겹친다. 따라서 “Flash가 공급 안정성·품질 모두 확실히 우월하다”거나 “Pro가 확실히 우월하다”는 통계적 결론은 아직 불가능하다.

더 중요한 것은 결함의 성격이다. Flash는 비승인 영문·숫자·순위·티커·의사문자를 더 자주 추가했고, 중복 캐릭터도 나왔다. scene00 재현에서는 정상 구도가 2/2 생성됐지만 `KOSPI` 또는 결정론 렌더 대상 `PER 4배`와 비승인 문장을 직접 그렸다. 비용과 관계없이, 이런 결함은 사실 정확성·OCR·후속 합성 비용을 증가시킨다.

### 2.3 현재 비교는 Flash의 최선 조건도, 운영 버튼의 정확한 조건도 아니다

현재 공통 provider payload에는 Flash의 `thinkingConfig`가 없다. [공식 GenerateContent 이미지 가이드](https://ai.google.dev/gemini-api/docs/generate-content/image-generation)에 따르면 기본은 `minimal`이므로 Stage2는 Flash High 품질 시험이 아니다. 반대로 비교 harness는 승인 내레이션 전체를 semantic basis로 노출하여 결정론 수치가 모델에 보이는 조건이었다. 이것이 운영 버튼의 실제 최종 payload와 동일하다고 아직 증명되지 않았다.

그러므로 지금 모델을 교체하면 두 변수가 섞인다.

- 모델 차이: Pro 대 Flash.
- harness·프롬프트 계약 차이: 결정론 수치 노출, 오염된 완성 장면 참조, thinking 설정 누락.

먼저 공통 입력 계약을 동일하게 만들어야 모델 비교가 유효하다.

## 3. 왜 Pro Standard만 고집하는 것도 최선이 아닌가

Pro의 반복 503은 로컬 코드만의 현상으로 보기 어렵고 [외부 개발자 포럼](https://discuss.ai.google.dev/t/gemini-image-api-503-unavailable-high-demand-on-gemini-3-pro-image-preview/126785)에서도 high-demand 사례가 보고됐다. [공식 최적화 문서](https://ai.google.dev/gemini-api/docs/optimization)는 Priority가 중요한 요청을 비차단 큐로 라우팅하고, Priority 용량을 넘으면 Standard로 완화한다고 설명한다. [현재 가격표](https://ai.google.dev/gemini-api/docs/pricing)에서 Pro Image는 Priority를 지원하지만 Flash Image에는 Standard·Batch만 제시된다.

비용을 신경 쓰지 않는 이번 판단에서는 **모델을 바꾸기 전에 Pro Priority로 동일 품질 분포를 유지하면서 가용성을 시험하는 것**이 가장 깨끗한 실험이다. 다만 다음은 실측 전 확정하지 않는다.

- 현재 Gemini Developer API 호출 경로에서 해당 계정·모델이 Priority payload를 실제 수용하는지.
- Priority가 이 프로젝트의 503을 몇 % 줄이는지.
- Priority 초과 시 Standard 완화가 원장에 어떻게 나타나는지.

## 4. 외부 구현과 커뮤니티에서 얻을 수 있는 것

오픈소스 도구들은 한 모델로 전역 고정하기보다 모델과 thinking level을 옵션으로 노출하거나, Flash를 일반 기본·Pro를 복잡 작업 선택지로 둔다. 이는 “평균적으로 빠른 모델 하나”보다 작업 유형별 선택이 실용적이라는 설계 사례다.

포럼에는 Pro와 Flash 모두의 503·출력 결함 사례가 있다. 하지만 사용자 구성, preview/GA 시점, 지역, quota, payload가 달라 빈도를 직접 비교할 수 없다. 따라서 커뮤니티 자료는 다음만 말해준다.

- Pro 503은 이 저장소만의 고유 현상은 아니다.
- Flash도 무결점 공급자나 무결점 출력 모델은 아니다.
- 결제 등급·모델 변경 하나만으로 장애가 사라진다고 가정하면 안 된다.

운영 정책은 공식 계약과 이 저장소의 쌍대 실측을 중심으로 정한다.

## 5. 권장 구현·검증 순서

### 5.1 모델 비교 전에 공통 계약을 고정

1. 실제 영상 생성 버튼의 `images_worker` 최종 payload를 캡처한다.
2. 승인 대본 중 모델이 이해해야 할 의미와 결정론 렌더 대상 문자열·수치를 분리한다.
3. `PER 4배`, 지수값, 등락률 등은 모델에게 그리라고 노출하지 않는다. 필요한 의미는 구조화된 비문자 시각 지시로 전달한다.
4. 완성된 Job52 장면을 그대로 style reference로 쓰며 딸려오는 문자·수치·신체 비례 오염을 정화한다.
5. model ID, thinking level, service tier, prompt hash, 참조 SHA-256을 요청 원장과 fingerprint에 포함한다.

이 변경은 Stage2 fixture에만 적용하지 않고 영상 생성 버튼이 타는 공통 운영 경로에 적용한다.

### 5.2 두 개의 비교 레인

- 레인 P: `gemini-3-pro-image`, Priority.
- 레인 F: `gemini-3.1-flash-image`, `thinkingLevel=high`, Standard.

동일한 승인 scene contract, 정화된 참조, 동일 출력 해상도, 각 1회 쌍대 요청으로 비교한다. 공급자 실패와 품질 실패를 분리한다.

### 5.3 최소 대표 유형

Job52 번호 자체가 아니라 다음과 같은 일반 유형에서 표본을 뽑는다.

1. 교실·설명형: 정확한 승인 용어와 물리 비유.
2. 관제실·데이터형: 복수 물리 표면과 높은 정보 밀도.
3. 뉴스·위기형: 복잡한 배경과 캐릭터 해부학.
4. 분할 상승/하락형: 좌우 공간 관계와 상반된 의미.
5. 대화·감정형: 얼굴·의상·표정 다양성과 캐릭터 정체성.
6. 텍스트 없는 물리 비유형: Flash의 속도·밀도 이점을 분리 측정.

### 5.4 결함을 하나의 점수로 뭉치지 않음

장면마다 다음을 별도 기록한다.

- HTTP 상태·지연·usageMetadata.
- 승인 문자열 정확성, 접두·접미·따옴표·의사문자, 비승인 문자열.
- LLM이 직접 생성하면 안 되는 금융 수치 노출.
- 캐릭터 해부학, 얼굴 4영역(sclera/홍채/동공/catchlight), 손·팔다리.
- Job52 기반 화풍과 정보 밀도.
- 스크립트 의미·소품·물리 표면의 연결.
- 사용자 육안 승인.
- Fal 후보 여부: 문자·수치 표면은 고정하고 사물·배경·캐릭터 동작만 허용 가능한지.

### 5.5 전환 기준

Flash를 전역 기본값으로 바꾸려면 평균 미감이 아니라 치명 결함에서 Pro 대비 비열등을 보여야 한다.

- 최소 59개의 독립 출력에서 치명 결함 0건이면 “치명 결함률 5% 미만”의 근사 95% 상한(rule of three)을 주장할 수 있다.
- HTTP·텍스트·해부학·의미·화풍을 각각 보고한다.
- 한 유형에서만 성공한 결과를 전체 주제로 일반화하지 않는다.
- 59장 기준 전에도 특정 유형에서 반복 우세가 확인되면 그 유형만 명시적으로 Flash로 라우팅할 수 있다.

## 6. 세 가지 큰 목표와의 연결

### 목표 1 — 시간 보정·자막 청크·TTS/이미지 싱크

모델 전환 자체는 목표 1을 해결하지 않는다. 이미지 모델에는 승인된 장면 청크와 실제 TTS 타이밍에서 확정된 장면 의미만 전달해야 한다. 모델 라우터가 장면을 합치거나 나누지 않으며, 모델 차이로 이미지 재시도 횟수가 달라져도 자막 원문·TTS 음성·청크 경계는 바뀌지 않아야 한다.

### 목표 2 — 스크립트 의미를 충실히 반영하는 이미지

Flash는 빠르고 밀도 높은 장면을 만들 가능성이 있으나, Stage2에서는 비승인 장식 정보도 더 많이 추가했다. 따라서 의미 충실도는 “요소가 많음”이 아니라 승인 scene contract의 의미 객체가 정확히 존재하는지로 판정한다. 유형별 라우팅은 이 목표를 강화하기 위한 수단이다.

### 목표 3 — 오탈자·이탈자·수치 정확성 및 Fal 안전성

현재 가장 강한 Pro 유지 근거다. Pro도 완벽하지 않지만 승인 문자열 정확성에서 더 안정적이었다. 정보성 문자열과 금융 수치는 결정론 렌더를 유지하고, 모델이 만든 base raster의 비승인 텍스트는 strict OCR·국소 재판독으로 거절한다. Fal은 텍스트·수치 표면을 움직이지 않고 캐릭터·사물·배경의 안전한 동작만 적용한다. 모델 변경이 이 불변식을 완화하지 않는다.

## 7. 즉시 적용할 의사결정

| 질문 | 결정 |
|---|---|
| 지금 전역 Flash 전환? | 아니오. |
| 현재 버튼 기본 모델? | Pro 유지. |
| 503 개선의 첫 실험? | Pro Priority 소규모 canary. |
| Flash 추가 검증? | 예. High thinking을 명시한 쌍대 shadow/canary. |
| 503 시 자동 Flash 폴백? | 아니오. 명시적 라우팅·새 fingerprint·전 게이트 재검증 필요. |
| 장기 구조? | 유형·계약 기반 Pro/Flash 선택 라우터가 유력. |
| 비용 때문에 실험 축소? | 아니오. 다만 정보 포화 시 목적 없는 추가 호출은 중단. |

## 8. 한계와 미확정 사항

- Stage2 47장은 같은 Job52 계열이고 다양한 미래 주제를 완전히 대표하지 않는다.
- Flash High와 Pro Priority의 실제 쌍대 결과는 아직 없다.
- Stage2 harness의 결정론 수치 노출이 운영 버튼에서도 발생하는지는 최종 payload 감사 전 미확정이다.
- 공개 벤치마크는 이 채널의 한국어 금융 텍스트·캐릭터·화풍 계약을 직접 측정하지 않는다.
- Priority의 실제 503 감소율은 공급자 보장이 아니라 이 저장소에서 측정해야 할 값이다.
- 이 문서는 정책 연구 결과이며 모델 설정을 변경하거나 유료 API를 호출하지 않았다.
