# V5 Archetype 확장 통합 검토: 기존 4개와 신규 4개

작성일: 2026-07-31  
상태: **설계 검토 완료, 코드·이미지 API 호출 미실행**

관련 기준 문서: [V5 Primary Surface Archetype 검증 플레이북](V5_PRIMARY_SURFACE_VALIDATION_PLAYBOOK.md)

## 1. 검토 결론

`data_lab`, `trade_calculator`, `risk_control_room`에서 통과한 primary-surface 검증 로직은 기존 미검증 4개와 아래의 신규 후보 4개에도 적용할 수 있다. 단, 이것은 "같은 프롬프트 문장으로 해결된다"는 뜻은 아니다.

**공통 원칙은 유지하고, primary의 물체 지정·대체물 금지·비-primary 소품 목록은 archetype마다 새로 작성해야 한다.** 특히 화면·게시판·가격표가 많은 무대일수록 모델이 그럴듯한 다른 표면으로 글자를 옮길 위험이 높다.

새 4개 후보는 현 시점에서는 아래 이름으로 설계 검토를 진행하는 것이 적합하다.

| 후보 코드명 | 검토 결론 | 이유 |
|---|---|---|
| `earnings_stage` | 유지 | 분기 실적, 컨퍼런스콜, 어닝서프라이즈/쇼크를 기존 7개와 다른 "발표 무대"로 표현한다. |
| `real_estate_office` | 유지 | 주택 가격·대출 금리·거래량을 공간과 물건의 맥락으로 설명할 수 있다. |
| `briefing_podium` | **`interview_podium`에서 이름 조정 제안** | CEO 인터뷰와 정책 브리핑을 함께 포괄하고, 단순 인물 인터뷰보다 발표대·브리핑 벽이라는 물리 무대를 분명히 한다. |
| `job_market_hall` | 유지 | 고용·실업률·채용·구인난을 경제 뉴스의 독립된 공간으로 다룬다. |

`briefing_podium`은 제안 단계의 이름일 뿐이다. 코드 반영은 사용자의 다음 승인 뒤에만 한다.

## 2. 플레이북 5원칙의 기존 7개 적용성

플레이북의 5원칙은 다음과 같다.

1. primary 물체를 위치·형상까지 정확히 지정
2. 독립 명패·카드·화면 등 그럴듯한 대체물을 명시적으로 금지
3. primary 외 소품을 전수 열거해 비문자로 제한
4. primary에 읽을 수 있는 장식 영문/표본 수치 2~3개를 의무화
5. AI 문자·숫자와 검증 사실값을 분리하고, 사실값은 결정론적으로 합성

| 기존 archetype | 적용 가능성 | 적용할 때의 핵심 조건 | 현재 상태 |
|---|---|---|---|
| `data_lab` | 가능, 검증됨 | 중앙 홀로그램 지도만 정보 표면, 콘솔·보조 게이지는 비문자 | 통과·규칙 동결 |
| `trade_calculator` | 가능, 검증됨 | 저울 중앙 기둥 바로 아래의 넓은 받침을 지정하고 독립 명패를 금지 | 통과·규칙 동결 |
| `risk_control_room` | 가능, 검증됨 | 단일 중앙 게이지 문자반만 허용하고 상자·우산까지 비문자 목록에 포함 | 통과·규칙 동결 |
| `weather_map` | 가능 | 지도 벽 전체가 하나의 물리 표면이다. 도시·구름·화살표가 여러 위치여도 모두 **같은 지도 벽 안**에만 있어야 한다. 카메라·독립 예보판에는 글자를 금지한다. | 미검증 |
| `classroom` | 가능 | 중앙 녹색 teaching wall만 판서 표면으로 허용한다. 핀 메모, 책, 책상, 램프는 글자를 담기 쉬우므로 명시적으로 비문자화한다. | 미검증 |
| `port_emergency` | 가능하지만 위험 높음 | 컨테이너 1개 면만 primary로 지정한다. 다른 컨테이너의 운송 스텐실·선박명·세관 표지로 글자가 새기 쉬워 전체 컨테이너를 개별 관리해야 한다. | 미검증 |
| `retail_shock` | 가능하지만 위험 가장 높음 | 체크아웃 장치에 결합된 영수증 표시 창만 primary로 허용한다. 진열 상품·가격표·세일 태그·별도 POS 화면은 모두 텍스트 대체물 위험이다. | 미검증 |

### 기존 4개에 대한 판정

네 원칙은 모두 적용 가능하다. 다만 `weather_map`의 지도 안 여러 라벨은 **여러 소품으로의 분산이 아니라 하나의 곡면 지도 벽 안의 배치**이므로 허용된다. 반대로 `port_emergency`의 여러 컨테이너는 모두 비슷해 보여도 서로 다른 물체이므로, 하나의 컨테이너 이외에는 읽을 수 있는 스텐실을 금지해야 한다.

## 3. 플레이북 절차의 신규 4개 적용성

플레이북 8장의 체크리스트는 신규 archetype에도 그대로 쓸 수 있다.

| 플레이북 절차 | 신규 archetype 적용 방식 | 추가 주의점 |
|---|---|---|
| stage/props 전수 조사 | 코드 추가 전, 아래 표의 명시 소품·대체 위험을 설계 계약으로 확정한다. | 신규 무대는 아직 `ARCHETYPES`에 없으므로 이 표 자체가 최초 계약이 된다. |
| primary 1개 지정 | 큰 벽·매립 보드처럼 프레임 전체에 붙은 물체를 우선 선택한다. | 작은 연단 명패, 제품 가격표처럼 독립 카드로 보이는 표면은 primary로 피한다. |
| 대체물 금지 | 일반 대체물 + 업종별 대체물을 모두 exclusions에 적는다. | "스크린"은 유용하지만 독립 대시보드가 되기 쉬우므로, 벽에 매립된 하나의 표면으로 한정한다. |
| primary 의무화 | 해당 표면에 장식 영문 2~3개·표본 수치·간단한 그래프/다이어그램을 요구한다. | 정확한 실적·금리·고용 수치를 AI 문자에 맡기지 않는다. |
| 단일 호출·사후 대조 | 한 archetype당 1장, 자동 재시도 없음, 원장과 API 로그 및 콘솔 대조 | 신규 코드와 새 프롬프트 변경을 한 번에 여러 개 검증하지 않는다. |

## 5. 신규 후보의 primary 설계 판단

### 작은 명패보다 벽 매립 표면을 우선하는 이유

사용자 제안 중 `earnings_stage`의 발표대 자료판, `interview_podium`의 연단 명패, `job_market_hall`의 전광판은 정보 표면이 될 수 있다. 그러나 작은 명패·전광판은 다음 두 위험이 크다.

- 별도의 UI 카드나 LCD 위젯처럼 보일 수 있다.
- 대형 배경의 다른 그럴듯한 카드로 정보가 이동해도 사람이 발견하기 어렵다.

따라서 1차 검증에서는 무대에 **고정·매립된 넓은 벽면**을 primary로 삼는 편이 `data_lab`의 성공 조건에 가장 가깝다. 이후 영상 문법상 연단 명패나 영수증 창이 꼭 필요한 경우에만, `trade_calculator`처럼 물체 위치를 더 정밀하게 지정한 별도 검증을 한다.

## 6. 권장 검증 순서

### 결론: (a)를 기본으로 하고, (b)는 설계 검토 그룹에만 사용

실제 유료 생성 검증은 **기존 4개를 먼저 끝내는 순차 방식 (a)**을 권장한다. 신규 archetype을 같은 날 병렬로 실행하지 않는다.

이유는 다음과 같다.

1. 기존 4개는 이미 코드의 `ARCHETYPES`와 `ARCHETYPE_SURFACES`에 존재한다. 문제 발생 시 primary 계약의 결함인지 새 무대 설계의 결함인지 분리하기 쉽다.
2. 신규 4개는 stage, props, 표면, substitutions가 모두 새 변수다. 기존 미검증 무대와 함께 실패하면 원인을 좁히기 어렵다.
3. `retail_shock`처럼 정보 패널과 가장 가까운 기존 실패 위험을 먼저 해결해야 `real_estate_office`, `job_market_hall`의 가격표·게시판 위험을 더 빨리 다룰 수 있다.

다만 **설계 문구 검토**는 구조가 가까운 그룹으로 묶어 재사용한다.

| 검증 선행 archetype | 이후 참고할 신규 archetype | 재사용할 교훈 |
|---|---|---|
| `weather_map` | `earnings_stage`, `briefing_podium` | 큰 벽 매립 표면 하나에만 정보를 넣고, 카메라·발표대·보조 스크린을 비문자로 유지 |
| `classroom` | `real_estate_office` | 넓은 고정 벽면과 작은 종이/서류/책상 소품을 분리 |
| `retail_shock` | `job_market_hall`, `real_estate_office` | 가격표·영수증·게시물·번호표가 독립 카드로 새지 않게 막는 방법 |
| `port_emergency` | 신규 무대 공통 | 테마형 서사 소품(컨테이너·표지·소품)에 문자 누출이 생길 때 전수 금지 목록을 만드는 방법 |

### 실제 실행 순서 제안

```text
기존: weather_map → classroom → port_emergency → retail_shock
  ↓ (4개 모두 통과·콘솔 대조 뒤)
신규: earnings_stage → briefing_podium → real_estate_office → job_market_hall
```

각 화살표는 **직전 archetype의 이미지 판정과 콘솔 대조가 완료된 뒤**에만 진행한다. 같은 그룹이라는 이유로 자동 실행하지 않는다.

## 7. 코드 반영 전 승인 항목

신규 archetype을 `ARCHETYPES`, `ARCHETYPE_SURFACES`, `TYPE_CANDIDATES`, 프롬프트의 archetype별 substitute ban에 추가하려면, 먼저 다음을 승인받아야 한다.

- [ ] `briefing_podium` 명칭 및 위 4개 무대 계약 확정
- [ ] 각 후보의 primary 문장과 primary 외 비문자 목록 확정
- [ ] 각 후보의 테마 대체물 금지 문구 확정
- [ ] 기존 미검증 4개를 먼저 검증한다는 순서 확정
- [ ] 코드 반영 후 프롬프트 문자열만 보는 무상 검증 승인
- [ ] 그 다음 archetype별 1장 유료 호출 승인

## 8. 아직 하지 않은 일

- 신규 4개 archetype 코드 추가
- scene_type → 신규 archetype 추천 규칙 추가
- 신규 archetype 이미지 생성
- 실제 기업 실적, 금리, 부동산, 고용 지표를 AI 프롬프트에 삽입
- 실수치 오버레이의 좌표·글꼴·원근 합성 구현

즉 이번 문서는 **무대를 늘려도 primary-surface 검증 규칙이 무너지지 않는지 확인하고, 새 무대가 생길 때의 계약을 먼저 고정한 설계 결과**다.
