# WO-IMG-01-C — 표면별 문자 위치·추세선 OCR·의미 라우팅

## 1. 결론: 코드 계약 구현, 유료 파일럿 승인은 아님

요청한 WO-B 긍정 사례를 먼저 보완했다. 이어 WO-C의 **선택형 문자 계약, 실제 문자별 위치 원장, 추세선 네 역할의 최종 OCR 연결**을 구현했다.

후속 C-2에서 정상 추세선 OCR 오판의 직접 원인을 찾아 합성 fixture 기준으로 수정했다. 종료값 글자 셀 안으로 상승선과 화살표가 들어오던 배치를 분리한 뒤 정상 추세선은 통과하고 종료값 오염은 거절됐다. 다만 **WO-C 전체 완료 또는 8장 파일럿 준비 완료라고 판정하지 않는다.** 자동 물리 표면 확인, 원근 연결, 장식 문자 생성 허용 크기 실측, 실제 생성 이미지의 시각 품질 검토는 완료되지 않았다. 7절은 최초 실패 관측을 보존하고 10절에 C-2 수정 증거를 추가한다.

이번에는 유료 API 0회. scene42 동결 유지. Gemini 이미지 재생성, Claude/TTS/Fal 호출, MP4 조립, 운영 서비스 재시작/배포, 원격 push 및 Git 이력 정리를 하지 않았다. 테스트용 합성 PNG는 만들었으며 실제 Job52/54 이미지가 아니다.

## 3. 공용 입력/출력 계약

새 경로 선택은 scene의 `text_render_policy="semantic_roles_v1"`로 명시한다. 기존 Job을 일괄 변환하거나 기존 일반형·캐릭터·V5/archetype 계약을 폐기하지 않는다.

```text
검증 사실 ─→ WO-B 완전값 검증 ─→ 수치 역할(label/value/start/end)
승인 화면 문구 ─→ 의미 라우팅 ─→ 문구/표면 계획
                                  ↓
원본 이미지 SHA-256 + 명시적 승인 표면 bbox
                                  ↓
결정론 렌더 + 실제 글자 bbox 원장
                                  ↓
역할·표면별 최종 래스터 crop → 실제 OCR → 공백류만 정규화한 정확 대조
                                  ↓
전체 통과 시에만 새 선택 경로의 파일 교체
```

주요 파일:

- `app/utils/image_text_contract.py`: 정보성/장식성 라우팅의 공통 계약.
- `app/v5/scene/runtime_contract.py`: V5 계획도 같은 계약을 소비. 새 정책에서는 결정론 문구를 생성 허용 목록과 표면 텍스트 생성 지시에서 제외.
- `app/services/surface_text_manifest.py`: 실제 잉크 bbox, 역할 ID, 표면 bbox, 계약 해시, 프레임 크기.
- `app/v5/overlay/diegetic_fact_overlay.py`: 기존 글꼴·색을 사용하면서 수치 역할별 좌표를 기록.
- `app/services/semantic_surface_text.py`: 승인 표면 확인, 임시 파일 렌더, 최종 판독, 원자적 교체, 재개 시 재판독.
- `app/services/final_frame_text_integrity.py`: 문자 셀별 OCR 연결 및 fail-closed 대조.
- `app/workers/images_worker.py`: 새 정책 선택 분기만 추가. 기존 미커밋 worker 변경 전체를 이번 커밋에 섞지 않았다.

## 4. 정보성/장식성 라우팅

| 입력 성격 | 새 정책의 경로 | 의미 |
|---|---|---|
| 한국어/영어 정보 문구 | 결정론 문자 셀 | 언어 자체를 금지하지 않음 |
| 수치·날짜가 포함된 문구 | 검증 사실 오버레이 | 일반 문자 계획으로 수치 근거 검증을 우회할 수 없음 |
| 명시적으로 장식성인 비수치 문구 | 현재 결정론 경로 | `decoration_size_calibration_pending` 기록 |
| 장식성이라고 분류된 숫자 | 정보성으로 처리 | purpose 변경으로 숫자 보호를 해제할 수 없음 |
| 장면 승인 목록 밖의 계획 문구 | 거절 | 계획이 스스로 승인 목록을 확장하지 못함 |

`screen_text_validation.passed=True`가 필요하다. 이는 상류 승인 결과를 소비하는 것이지, 이 모듈이 언론사 팩트체크를 다시 했다는 뜻이 아니다. 수치의 근거는 별도로 기존 `verified_facts` 어댑터를 통과해야 한다.

`screen_texts`에 있는 수치가 동일한 오버레이 역할에도 있으면 중복 합성하지 않는다. 반대로 승인 문구가 일반 문자 계획에도, 오버레이 역할에도 없으면 거절한다. 누락을 `not_applicable`로 승인하지 않는 회귀도 추가했다.

**장식 문자 생성 허용은 아직 활성화하지 않았다.** 문자 높이/프레임 높이의 허용 비율을 실측한 적이 없으므로 임의로 수치를 정하지 않았다. `measured_min_character_height_ratio=None`을 남긴다. 이 선택 경로에서 최종 이미지를 무문자화하는 것은 아니다. 필요한 문구를 최종 래스터에 합성한다. 다만 실제 장면의 타이포그래피와 화풍이 사용자의 선호를 만족하는지는 별도 시각 검토가 필요하다.

## 5. 표면 연결과 위치 보장 범위

새 일반 문자 계획은 `text`, `surface`, `purpose`를 갖는다. `surface_bindings[surface]`는 다음을 갖는다.

```json
{
  "bbox": [0.05, 0.10, 0.40, 0.50],
  "image_sha256": "승인한 원본 이미지의 실제 SHA-256",
  "validated": true
}
```

`bbox`는 정규화된 `[x,y,width,height]`이다. 원본 이미지 해시가 다르거나 승인 연결이 없으면 중단한다. 새 정책의 수치 오버레이도 승인된 surface를 참조하고 그 bbox 안에 있어야 한다.

각 실제 문자열의 `surface_text_manifest.cells`에는 다음이 남는다.

- `id`: `overlay:0:start_value`, `plan:1:text` 등.
- `text`: 승인 문자열 그대로.
- `bbox`: Pillow `textbbox` 기반 픽셀 좌표 + 2px 여유.
- `anchor_bbox`: 이 문자열이 속한 승인 표면의 픽셀 범위.
- `font_size`, `psm_modes`.

전체 원장은 프레임 크기와 입력 계약 SHA-256을 가진다. 누락·중복 ID, 문구 변경, 표면 교환, 잘림, 겹침, 판독 모드 변경, 오래된 계약/프레임 크기는 거절한다. 같은 문구가 두 표면에 필요하면 두 셀로 검증하며 전역 중복 제거로 한쪽 누락을 숨기지 않는다.

**후속 상태:** 이 문단의 `validated=True` 자기 승인 한계는 WO-IMG-01-C3에서 제거했다. 현재는 실제 원본 픽셀·해시·프레임·내부 문자·가림을 재검증하며, binding이 없는 단일 표면은 외부 비전 없이 로컬 픽셀로 연결한다. 다중 별도 표면과 원근 표면은 계속 차단한다. 상세 증거는 [C3 문서](WO_IMG_01_C3_PHYSICAL_SURFACE_AND_PILOT_GATE_2026-08-27.md)를 참조한다.

OCR 검사는 계획된 셀 안의 글자를 검사한다. **다른 영역에 생성 모델이 임의로 쓴 글자가 없다는 전체 프레임 보장과는 다르다.** 기존 시각 QA/전체 이미지 텍스트 검수는 계속 필요하다.

## 6. 추세선 시작/종료값 연결과 발견한 배치 문제

기존 최종 검사에는 추세선의 시작·종료값 위치 계약이 없었다. label/value만으로 통과시키는 대신 `unsupported_surface_layout`으로 보류하던 경로에 실제 렌더 좌표를 연결했다. 새 렌더는 **label, value(변화량), start_value, end_value**를 각각 기록한다.

실제 좌표를 기록하자 기존 추세선 렌더의 종료값과 변화량이 겹치는 문제도 확인했다. 1280×720 합성 fixture에서 초기 좌표는 다음이었다.

| 역할 | 초기 bbox |
|---|---|
| 종료값 `2.75%` | `[912,250,1141,314]` |
| 변화량 `0.25%p` | `[772,251,1083,332]` |

두 영역이 교차한다. 현재 구현은 종료값을 화살표 아래로, 변화량을 제목 우측으로 분리한다. 글꼴·색·도형의 기존 표현을 전면 교체하지 않는다. 긴 문구가 여전히 넘치거나 겹치면 값을 축약하지 않고 거절한다.

최종 OCR은 각 실제 문자 crop을 독립 판독한다. 한 줄은 PSM 6/7, 줄바꿈 문구는 PSM 6이다. 여러 판독의 부분 결과를 이어 붙이거나 불일치 관측을 버리고 통과시키지 않는다. 공백/줄바꿈만 무시하고 숫자·부호·단위·대소문자는 그대로 대조한다.

새 문자 셀 경로에는 기존 단일 캡션의 픽셀 provenance 예외를 적용하지 않는다. OCR 불일치는 보류된다. 또한 좌표 없는 mock 행 주입은 새 경로에서 `spatial_ocr_required`로 거절한다. 단위테스트는 실제 crop 코드가 호출하는 판독 함수만 mock으로 대체하며, 이것을 실제 OCR 성공으로 보고하지 않는다.

판독 사본에는 빈 외곽 여백, 배경 극성 정리, 행당 64px 크기 정규화를 적용한다. **이 64px는 로컬 OCR 전처리 값이지 장식 문자 생성 허용 크기나 화풍 기준이 아니다.** 원본 이미지의 문자 크기와 승인 문자열을 바꾸지 않는다.

## 7. 실제 OCR 결과 — 정상 추세선은 아직 거절됨

실행: `54bada8` 커밋만 추출한 사본의 `scripts/audit_surface_text_cells.py`.

환경: Tesseract 5.5.0, `kor+eng`, `/usr/share/fonts/truetype/nanum/NanumGothicBold.ttf`, 합성 1280×720 래스터. 외부 소켓을 차단했고 Gemini/언론사 자료/기존 Job 이미지를 사용하지 않았다.

원문: [real-ocr.json](evidence/wo_img_01_c_surface_text_20260827/real-ocr.json). 이미지 해시, scene 계약, 각 셀/PSM의 recognized, exact_match, missing 결과를 보존한다.

| 실제 합성 래스터 | 기대 | 실제 | 해석 |
|---|---|---|---|
| `현재 전망` / `수정 전망`, 올바른 두 위치 | 통과 | 통과 | 정상 문자열과 위치의 긍정 사례 |
| 두 문자열의 위치를 교환 | 거절 | 거절 | 단어가 모두 존재해도 위치가 틀리면 거절 |
| 정상 추세선 | 통과 | **거절** | 정상값을 읽지 못하는 false negative가 남음 |
| 종료값을 `2.75%` 대신 `2.85%`로 그린 추세선 | 거절 | 거절 | 단, 정상 추세선도 실패하므로 이것만으로 유효한 민감도 입증은 아님 |

정상 추세선에서 시작값 `2.50%`, 변화량 `0.25%p`는 두 PSM 모두 맞게 읽었다. 종료값 `2.75%`는 두 PSM 모두 `7.15%`로 읽었고, 제목 `인상폭`은 PSM 6의 여러 오판 조각과 PSM 7의 정상 결과가 불일치했다. 따라서 전체는 거절됐다. 기대 문자열로 OCR 출력을 교정하거나 유사도/부분 문자열 매칭을 복구하지 않았다.

**이는 실제 로컬 OCR에서 관측한 오류다.** 기존 WO-A/B의 가짜 OCR 행 또는 scene 객체 재현과 다르다. 다만 합성 시험 이미지이며 실제 Gemini 산출물의 실패율을 측정한 것은 아니다. 제목·종료값 오판의 세부 원인을 단일 폰트/해상도/공급자 문제로 확정하지 않는다.

## 10. C-2 후속: 글자 크기가 아니라 도형 간섭이 직접 원인이었음

### 10.1 수정 전 스윕

`audit_trend_ocr_sweep.py`로 동일한 합성 추세선을 실제 Tesseract 5.5.0에 넣었다.

- 렌더 글자 크기: 기준의 `0.75, 0.85, 1.0, 1.15, 1.30배`.
- OCR 사본 높이: `64, 80, 96px`.
- 원본 배경 여백: `6, 12px`.
- 추가 백지 여백: `16, 32px`.
- 회색조/임계값 160 이진화.
- 각 역할에 미리 선언된 PSM을 모두 실행하고 모든 결과가 정확해야 통과.

배치 수정 전에는 네 역할이 모두 맞는 전처리 설정이 **0개**였다. 글자 크기를 0.75~1.30배로 바꿔도 렌더 전체는 5/5 모두 실패했다. 따라서 `48px 이상` 같은 단일 크기 임계값을 채택할 근거가 없었다.

역할별 실측은 원인을 더 좁혔다.
