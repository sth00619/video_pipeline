# V5 개발 검토안 — 레퍼런스 기반 고밀도 경제 설명 카툰 장면

- 문서 상태: **개발 검토용 / 구현 승인 전**
- 작성일: 2026-07-27
- 대상 저장소: `video_pipeline`
- 선행 기반: V2.2/V3 정보 표면 합성, V4 정보 장면 템플릿, Gemini 이미지 생성, 기존 Kling 모션 경로
- 목표: 기존의 "빈 칠판/빈 모니터 + 후처리 도표" 중심 경로를 확장하여, **장면·캐릭터·상징 소품·사실 오버레이가 함께 작동하는 독자적 경제 설명 카툰**을 생성한다.

> 이 문서는 레퍼런스의 로고·마스코트·구체적 캐릭터 디자인을 복제하는 계획이 아니다. 추출 대상은 고밀도 경제 설명 카툰의 구도·정보 배치·연출 문법이며, 우리 채널의 캐릭터와 스타일 자산은 독자적으로 제작한다.

---

## 1. 문제 정의와 V4의 한계

V4는 정확한 한글·수치를 이미지 안의 검출된 보드 표면에 워프 합성하는 데 성공했지만, 레퍼런스와 비교하면 다음 차이가 남는다.

| 항목 | V4 현재 방식 | V5 목표 방식 |
|---|---|---|
| 장면의 출발점 | 빈 보드/모니터가 있는 배경 | 주장에 맞는 완결된 무대·행동·상징물 |
| 정보 밀도 | 보드 안의 카드·화살표 중심 | 프레임 전역의 지도·저울·계산기·항구·구름·차트 실루엣 등 |
| 캐릭터 | 보드 옆 설명자 | 화면의 25~50%를 차지하는 전경 주인공 |
| 텍스트 | 보드 내 후처리 중심 | 정확한 사실은 후처리, 배경의 비사실 장식 그래픽은 생성 모델 |
| 구도 제어 | 생성 결과에서 표면을 검출 | 생성 전에 SVG 레이아웃으로 캐릭터·소품·오버레이 영역을 예약 |
| 품질 판정 | 보드 검출 성공 여부 | 캐릭터 일관성, 정보 밀도, 구도, 오버레이 여유, 사실성까지 점수화 |

V5는 V4의 워프·가림·타이포그래피를 폐기하지 않는다. V4는 정확한 사실 오버레이의 하부 레이어로 유지하고, V5는 그 상위에 **장면 기획·멀티 참조 생성·품질 게이트**를 추가한다.

## 2. 레퍼런스에서 추출한 시각 문법

첨부 레퍼런스에서 확인한 공통점은 다음과 같다.

1. **무대가 매 장면 다르다.** 폭풍 항구, 계산대, 강의실, 방송 스튜디오, 거래 협상 무대, 데이터 연구실, 무역 계산실 등 주제마다 은유가 달라진다.
2. **전경 마스코트가 크다.** 장면 목적에 따라 화면의 약 25~50%를 차지하며, 표정·의상·손동작이 설명의 감정을 전달한다.
3. **세 레이어 이상의 깊이가 있다.** 전경 캐릭터/소품, 중경의 핵심 사건, 배경의 세트·차트·조명·날씨가 동시에 존재한다.
4. **정보는 한 보드에만 있지 않다.** 지도 위 구름, 금고 위 번개, 저울의 문서, 계산기, 모니터, 화살표, 차트 실루엣이 화면 전체에 배치된다.
5. **생성 텍스트와 사실 텍스트의 역할이 다르다.** 배경의 영어·수식·차트는 장식적이며 오류 가능성이 있다. 반면 한글 자막·말풍선·로고·검증 수치·날짜는 후처리 레이어로 관리해야 한다.
6. **스타일은 독자적인 카툰 규칙을 가진다.** 굵은 짙은 외곽선, 셀 셰이딩, 고대비 림라이트, 제한된 팔레트, 큰 표정, 연극적인 소품 배치가 반복된다.

### 2.1 장면 아키타입

| 아키타입 | 적합한 주장 | 시각 은유 | 필수 소품 |
|---|---|---|---|
| 항구 비상 | 공급망·관세 충격·수출 위험 | 폭풍, 번개, 경보 | 컨테이너, 선박, 크레인, 경광등 |
| 계산대 충격 | 가격 전가·소비자 부담 | 고액 계산·경고 | 계산기, POS, 영수증, 로봇/점원 |
| 강의실 해설 | 제도·정책·원인 설명 | 칠판 수업 | 칠판, 포인터, 노트북, 지도/흐름도 |
| 방송 지도 | 국가·지역별 차이 | 날씨 예보 | 대형 지도, 구름, 카메라, 포인터 |
| 양국 비교 무대 | 국가별 차등·협상 | 좌우 분할, 보호막/번개 | 국기 상징 상자, 커튼, 우산, 번개 |
| 무역 계산실 | 수치·합의·규정 | 저울과 계산 | 저울, 문서, 파이/막대 차트, 격자 |
| 데이터 연구실 | 산업·지역·추세 | 관제실 분석 | 지도, 모니터, 홀로그램 차트, 연구 복장 |

아키타입은 사실을 생성하지 않는다. 검증된 `claim_shape`와 `visual_metaphor`를 입력받아 어떤 장면 문법을 쓸지만 결정한다.

## 3. 반드시 지킬 책임 분리

### 3.1 생성 모델의 책임

- 독자 마스코트의 외형·의상·표정·포즈 유지
- 무대, 조명, 날씨, 소품, 지도 윤곽, 비사실 차트 실루엣, 빈 라벨판 생성
- SVG 스케치가 지시한 캐릭터 위치·시선·주요 오브젝트 배치 준수
- 장면의 감정과 경제적 은유 표현

### 3.2 결정론 렌더러의 책임

- 한글 자막, 말풍선, 채널 로고, 타임스탬프
- 검증된 금액·비율·날짜·지수·등락률
- 출처와 근거가 필요한 텍스트
- 정확한 영문 정책명·법령명·수치가 필요한 전경 라벨
- 최종 자막 안전영역, 로고 안전영역, 화면 비율 보정

이는 단순한 품질 선호가 아니라 프로젝트 규칙이다. LLM/이미지 모델이 수치형 금융 데이터를 만들어 내거나 이를 사실처럼 확정해서는 안 된다. 생성된 영어·수식은 사실 근거가 아닌 분위기 소품으로만 취급한다.

## 4. 목표 아키텍처

```text
검증 사실 + 스크립트
  → SceneBriefBuilder
      claim_shape / 감정 / 장면 아키타입 / 검증 오버레이 데이터
  → LayoutSketcher (신규, SVG + PNG)
      캐릭터 박스 / 상징 소품 3~5개 / 전경·중경·배경 / 안전영역
  → ReferencePack
      독자 캐릭터 시트 / 스타일 바이블 / 레이아웃 스케치
  → ImageProviderRouter (신규)
      Gemini Pro | Gemini Flash | BFL FLUX.2 klein / pro / max
  → QualityGate (신규)
      캐릭터·구도·정보밀도·빈 화면·안전영역·비용 검증
  → V4 정보 표면 + DeterministicOverlay
      한글·수치·출처·말풍선·자막·로고
  → Kling / FFmpeg
      제한된 구간의 모션, 최종 영상
```

### 4.1 `SceneBrief` 계약

```json
{
  "scene_id": "...",
  "tier": "hero | body | draft",
  "claim_shape": "external_rate | causal_chain | comparison | alert | trend | structure",
  "scene_archetype": "port_emergency | retail_shock | classroom | weather_map | split_stage | trade_calculator | data_lab",
  "emotion": "alarm | surprise | explain | confidence | concern",
  "character": {
    "pose": "point_left | present | alarmed_run | calculator_hold",
    "costume": "analyst | professor | reporter | safety_vest | formal",
    "frame_occupancy": 0.25
  },
  "metaphor_slots": ["storm", "cargo_ship", "warning_beacon"],
  "overlay_reservations": ["subtitle_bottom", "logo_top_right", "fact_callout_left"],
  "verified_overlay": []
}
```

- `frame_occupancy`는 0.25~0.50 범위만 허용한다.
- `metaphor_slots`는 3~5개를 요구한다. 한 개의 빈 보드만 있는 장면은 V5에서 실패로 판정한다.
- `verified_overlay`는 출처 참조가 있는 값만 허용한다.

### 4.2 `LayoutSketcher`

코드가 AI 생성 전에 SVG와 PNG 스케치를 만든다.

- 캐릭터 실루엣 박스와 시선/포인터 방향
- 전경·중경·배경 오브젝트 슬롯
- 로고(우상단), 자막(하단), 수치/말풍선 예약 영역
- 오버레이와 겹치면 안 되는 얼굴·손·핵심 물체 보호영역
- 장면별 16:9·9:16 파생 규칙

모델은 빈 화면을 만들라는 지시를 받지 않는다. 대신 스케치가 지정한 여백만 보존하고, 나머지는 장면 의미에 맞는 소품과 세트로 채운다.

## 5. 프로바이더 전략

### 5.1 기본 원칙

- 새로운 월 구독 도구는 도입하지 않는다.
- BFL·Google·fal 등 **이미 승인된 종량제 API**만 사용한다.
- 프로바이더 선택은 “시안/최종” 이분법이 아니라 장면의 복잡도, 참조 충실도, 비용 여유로 결정한다.
- 정확한 수치 텍스트의 유무는 라우팅 조건이 아니다. 그 값은 항상 후처리한다.

### 5.2 라우팅 정책 초안

| 조건 | 1차 프로바이더 | 보정/대체 | 이유 |
|---|---|---|---|
| 독자 마스코트가 크고 텍스트 의존이 낮은 본문 장면 | BFL FLUX.2 klein 9B | FLUX.2 Pro edit | 저비용 후보 생성과 캐릭터 시안 |
| 다수 소품·복잡한 구도·다중 참조가 필요한 히어로 장면 | Gemini 3 Pro Image | FLUX.2 Max 편집 또는 Gemini 재생성 | 복합 지시와 참조 구성 비교 |
| 일반 설명 장면 | Gemini 3.1 Flash Image | Gemini Pro | 비용·속도 균형 |
| 부분적인 의상/소품/배경 수정 | FLUX.2 Pro edit | Max/Flex | 기존 장면을 보존한 국소 편집 |
| 오프라인 대량 벤치마크 | Gemini Batch 또는 FLUX 후보 생성 | 없음 | 즉시성이 없는 평가 작업만 할인 경로 사용 |

Gemini 3 Pro는 최대 14개 입력을 받을 수 있으나, 고충실도 대상 수에는 제한이 있다. V5 요청에는 원칙적으로 **캐릭터 시트 1개 + 스타일 시트 1개 + 레이아웃 스케치 1개**만 넣어 참조 간 충돌을 줄인다. [Gemini 이미지 생성 문서](https://ai.google.dev/gemini-api/docs/image-generation)

BFL FLUX.2는 klein을 대량 시안, Pro를 편집, Max/Flex를 고난도 장면의 비교 후보로 쓴다. 실제 모델 선택은 벤치마크 결과로 확정한다. [BFL FLUX.2 가격](https://docs.bfl.ai/quick_start/pricing)

### 5.3 BFL 도입 범위

- 환경 변수: `BFL_API_KEY`만 사용하며, 키를 코드·문서·로그에 기록하지 않는다.
- BFL Provider는 잔액 API를 호출해 요청 전 잔액을 확인한다.
- 요청별로 모델, 해상도, 예상 USD, 환율 스냅샷, 원화 추정액, 실제 응답 상태를 비용 원장에 기록한다.
- BFL Direct API와 기존 fal FLUX 경로는 별도 Provider로 유지한다. 키/과금/엔드포인트를 혼용하지 않는다.
- LoRA/파인튜닝은 **V5의 선행조건이 아니다.** 독자 캐릭터 데이터셋의 권리·품질·재현성이 검증된 뒤 별도 승인으로 진행한다.

## 6. 비용 통제 설계

모든 상수와 상한은 `backend/spring-app/src/main/java/com/pipeline/video/config/PricingConfig.java`에 중앙화한다. FastAPI는 해당 정책을 읽어 preflight와 원장 기록에 사용한다.

### 6.1 영상 1건 예산 버킷

| 버킷 | 하드 상한 | 목적 |
|---|---:|---|
| 이미지 시안 | ₩3,000 | klein/Flash 후보 생성 |
| 최종 프레임 | ₩7,000 | Pro/Max/고난도 재생성 |
| 이미지 부분 보정 | ₩2,000 | 국소 편집, 최대 2회/장면 |
| 모션 | ₩15,000 | Kling 등 영상 구간 |
| TTS·음악 | ₩5,000 | 음성·음원 |
| 재시도 예비비 | ₩8,000 | 명시적 실패 재시도 |
| **합계** | **₩40,000** | 기존 절대 상한 |

환율은 코드에 하드코딩하지 않는다. 사전에 승인된 환율 공급원에서 일 단위로 가져와 캐시하며, 조회 실패 시 보수적 기본 상한 또는 해당 외화 요청 중단으로 처리한다. 선불 크레딧도 요청 시점의 사용량으로 원장에 적재하며 “이미 결제했으므로 0원”으로 처리하지 않는다.

### 6.2 호출 제한

- 시안: 씬당 기본 4장, 최대 6장
- 최종 생성: 씬당 최대 2장
- 편집: 씬당 최대 2회
- 품질 게이트 불통과 시: 자동 재시도 1회 후 수동 검토 큐 또는 기존 V4 cutaway로 강등
- 예산 버킷이 소진되면 상위 모델 재호출 금지; 저비용 모델 또는 결정론 렌더로 강등

## 7. 구현 작업 분해

### P0 — 계약·비용·Provider 기반

1. `ImageProvider` 인터페이스를 `generate`, `edit`, `estimate_cost`, `health_check`, `supports_references`로 확장한다.
2. `BflFluxProvider`를 추가한다. 시작 모델은 `flux-2-klein-9b-preview`와 `flux-2-pro-preview`로 한정한다.
3. `PricingConfig.java`에 버킷·프로바이더 가격 스냅샷·환율 정책·재시도 상한을 추가한다.
4. Redis/manifest 비용 원장에 `provider`, `model`, `request_kind`, `estimated_cost`, `actual_cost`, `currency_rate_snapshot`을 추가한다.
5. 키 누락·잔액 부족·API 4xx/5xx 시 즉시 실패 사유를 남기고, 빈 이미지/무료 폴백을 생성하지 않는다.

### P1 — 장면 기획과 스케치

1. `SceneBrief`와 장면 아키타입 레지스트리를 추가한다.
2. `LayoutSketcher`가 16:9 SVG/PNG를 만들도록 구현한다.
3. 아키타입별 최소 소품 수·캐릭터 점유율·안전영역을 계약으로 검증한다.
4. 기존 `InfoSceneTemplate`의 빈 보드 강제 프롬프트를 V5 경로에서 사용하지 않도록 분기한다.

### P2 — 프롬프트·참조 패키지

1. 독자 마스코트 스타일 바이블을 작성한다: 정면/3/4/측면, 표정 5종, 의상 5종, 손 포즈, 금지 요소.
2. 생성 요청을 `character_reference`, `style_reference`, `layout_reference`, `scene_brief`로 구조화한다.
3. 프롬프트에 “빈 보드”, “빈 모니터”, “단일 UI 카드”를 금지하고, 장면 아키타입의 소품·깊이·감정을 요구한다.
4. 생성 모델에는 한글·검증 수치·채널 로고를 요구하지 않는다.

### P3 — 품질 게이트와 오버레이

1. 비전 기반 또는 규칙 기반 점수: 캐릭터 면적, 캐릭터 위치, 소품 수, 빈 영역 비율, 안전영역 침범, 과도한 텍스트, 시각적 대비.
2. V4 정보 표면과 Pillow/FFmpeg 오버레이를 V5 예약영역에 합성한다.
3. 수치·한글·출처·자막은 원본 데이터 해시와 함께 manifest에 기록한다.
4. 배경의 의미 없는 생성 텍스트는 허용하되, 검증 사실로 취급하거나 내레이션과 연결하지 않는다.

### P4 — 벤치마크와 라우팅 확정

1. 고정된 8개 SceneBrief를 준비한다: 항구 비상, 계산대 충격, 강의실, 방송 지도, 양국 비교, 무역 계산실, 데이터 연구실, 일반 본문.
2. Gemini Pro, Gemini Flash, FLUX klein, FLUX Pro/Max 후보를 동일 스케치·참조·시드 정책으로 생성한다.
3. 장면별로 캐릭터 일관성·구도 충족·정보 밀도·오버레이 적합성·비용을 기록한다.
4. 단일 주관적 샘플이 아니라 평균 점수와 편당 원가로 기본 라우팅을 확정한다.

### P5 — 선택적 LoRA/파인튜닝

전제 조건을 모두 만족할 때만 별도 승인으로 진행한다.

- 레퍼런스 캐릭터가 아닌 독자 마스코트 데이터셋 20~30장
- 데이터셋 사용 권리와 채널 소유권 확인
- 기본 참조 방식 대비 캐릭터 드리프트가 임계값을 초과한다는 벤치마크 증거
- 파인튜닝 모델 ID, 비용, 삭제·교체·롤백 정책

LoRA는 V5의 품질 개선 수단이지, LayoutSketcher·참조 패키지·정확 오버레이를 대체하지 않는다.

## 8. 검증 기준

### 8.1 자동 테스트

1. BFL 키 부재/잔액 부족 시 이미지 작업이 시작 전에 실패하며 비용 원장에는 실패 원인이 남는다.
2. `SceneBrief`가 캐릭터 점유율·소품 수·예약영역 계약을 위반하면 생성 요청을 거부한다.
3. 동일 SceneBrief/스케치/시드의 요청 메타데이터가 재현 가능하다.
4. 검증 수치가 생성 프롬프트가 아니라 결정론 오버레이 입력에서만 온다.
5. 예산 초과 직전 요청은 실행되지 않으며, 상위 모델→하위 모델→cutaway 순으로 강등된다.
6. V4 및 V3 경로는 V5 비활성 시 기존 동작을 보존한다.

### 8.2 시각 QA 점수표

| 축 | 통과 기준 |
|---|---|
| 캐릭터 | 독자 캐릭터의 얼굴·색·외곽선·핵심 의상이 참조 시트와 일치 |
| 구도 | 캐릭터 25~50%, 최소 3개의 상징 소품, 전경/중경/배경 존재 |
| 정보 밀도 | 빈 배경·빈 보드가 주 화면 면적을 지배하지 않음 |
| 사실성 | 한글·수치·날짜·출처가 결정론 렌더로만 제공됨 |
| 가독성 | 자막·로고·말풍선 안전영역이 얼굴/손/핵심 물체를 가리지 않음 |
| 비용 | 호출 원가와 재시도 횟수가 버킷 안에 기록됨 |

V5 완료는 “한 장이 그럴듯해 보임”이 아니라, 8개 고정 장면에서 위 기준과 예산 조건을 동시에 통과하는 것으로 정의한다.

## 9. 비목표와 위험 관리

- 레퍼런스 채널의 로고·캐릭터·워터마크·고유 대사를 복제하지 않는다.
- 생성 모델의 숫자·영문 텍스트를 검증된 사실로 사용하지 않는다.
- BFL Key가 없거나 잔액이 없을 때 무료 이미지 폴백으로 조용히 바꾸지 않는다.
- LoRA 학습을 기본 기능으로 가정하지 않는다. 독자 자산·권리·벤치마크가 선행되어야 한다.
- 월 구독형 이미지 서비스는 백엔드 자동화 경로에 추가하지 않는다.
- 현재 작업트리의 기존 변경을 되돌리거나 V4를 삭제하지 않는다.

## 10. 구현 착수 전 결정 필요 사항

1. BFL Direct API Key를 개발 프로젝트에 설정할 권한
2. 독자 마스코트 디자인을 새로 만들지, 기존 소유 캐릭터 자산을 쓸지에 대한 결정
3. 벤치마크용 8개 검증 주제와 각 주제의 출처
4. 야간 Batch 처리 허용 여부 및 영상 제작 마감 시간
5. BFL 비용을 포함한 프로바이더별 일/주/월 지출 한도

위 다섯 항목이 정해지면 P0→P4를 순서대로 구현하고, LoRA는 벤치마크 결과를 보고 별도 결정한다.
